# Project Roadmap: retail-print-kit Integration

## Objective

Complete the incremental migration from the existing custom ESC/POS implementation to `retail-print-kit@0.4.0`.

The objective is to modernize the receipt-template, ESC/POS generation, and LAN printing layers without rebuilding or unnecessarily modifying the existing application architecture.

### Current Status

- Phase 1: Dependency and compatibility validation — completed.
- Phase 2: Declarative receipt template — completed.
- Phase 3: ESC/POS generation integration — completed.
- Phase 4: LAN printing integration — completed.
- Phase 5: Receipt preview integration — completed and validated.
- Phase 6 onward — pending.

Latest automated test result: 70/70 passing after Phase 5.

## Execution Strategy

Execute the following phases sequentially, one at a time.

You have authorization to proceed through all phases without requesting approval after each successful phase.

However:
- Never skip a phase or its validation.
- Never proceed with unresolved critical failures.
- Fix issues introduced by your own implementation before moving forward.
- If an issue cannot be resolved safely, stop and report it.
- Do not interpret passing unit tests as proof of physical printer compatibility.
- Preserve existing functionality throughout the migration.

## Phase 3 — ESC/POS Generation Integration

**Objective:** Build a production-ready ESC/POS generation module using the Phase 2 template and retail-print-kit.

Tasks:
1. Inspect the completed Phase 2 implementation.
2. Create a dedicated main-process printing module.
3. Convert receipt data into ESC/POS byte buffers using verified library APIs.
4. Handle ESC/POS initialization (`ESC @`), encoding, alignment, line feeds, and cutting.
5. Integrate barcode and QR generation where supported.
6. Implement logo bitmap rasterization using Electron `nativeImage` if compatible with the existing implementation.
7. Preserve CP437 encoding and existing 58mm/80mm printer profiles.
8. Retain the existing printing implementation as a fallback during migration.

Validation:
- Test initialization and command sequences.
- Test text encoding and special characters.
- Test barcode, QR, logo, and cutting operations.
- Compare old and new ESC/POS output for representative receipts.
- Verify buffer generation and error handling.
- Run all existing and newly added tests.

Do not modify the production print handler or network transport yet.

**Gate:** ESC/POS generation must be validated before Phase 4.

## Phase 4 — LAN Printing Integration

**Objective:** Replace the existing custom LAN ESC/POS printing implementation with retail-print-kit transport.

Tasks:
1. Integrate the new printing module into the existing `invoice:print` workflow.
2. Replace only the LAN ESC/POS printing branch.
3. Use the verified `NetTransport` API and configured TCP port.
4. Preserve existing timeout and connection settings.
5. Ensure proper connection lifecycle and resource cleanup.
6. Preserve existing IPC contracts and print-status transitions.
7. Handle connection failures, timeouts, partial failures, and printer disconnections.
8. Preserve existing error reporting and interrupted-print recovery.

Validation:
- Test successful TCP printing using a transport stub or controlled test server.
- Test connection refused and timeout scenarios.
- Test cleanup after success and failure.
- Verify print-status transitions in SQLite.
- Verify failed and interrupted jobs do not incorrectly become successful.
- Ensure no duplicate or unintended print attempts.
- Run the complete test suite.

Keep Windows system printing completely unchanged.

**Gate:** LAN printing integration must pass automated validation before Phase 5.

## Phase 5 — Receipt Preview Integration

**Objective:** Reduce differences between the receipt preview and actual ESC/POS output.

Tasks:
1. Evaluate `opsToHtml()` using the same operations generated by the new receipt template.
2. Determine whether it can replace or complement the existing React line-array preview.
3. Preserve existing preview interactions and application UI.
4. Support both 58mm and 80mm receipt widths.
5. Verify text wrapping, alignment, tables, logos, QR codes, and barcodes.
6. Avoid unnecessary renderer or component rewrites.

Validation:
- Compare preview output with generated ESC/POS operations.
- Test different receipt sizes and representative receipt data.
- Verify optional fields and long descriptions.
- Check that preview rendering does not interfere with printing.
- Keep the existing preview as a fallback if the new approach introduces regressions.

Important: HTML preview is not byte-exact with physical printer output. Document this limitation.

**Gate:** Preview integration must preserve existing UI behavior and pass regression tests.

## Global Engineering Rules

These rules apply to every phase:

1. **Backward compatibility:** Existing application behavior must remain intact unless explicitly covered by the migration.
2. **Minimal changes:** Modify only files necessary for the current phase.
3. **No speculative APIs:** Verify library APIs against the installed version and source.
4. **No unnecessary dependencies:** Avoid optional native modules and unrelated packages.
5. **Error handling:** Never silently swallow printing or transport errors.
6. **Data integrity:** Never compromise SQLite records or print-status consistency.
7. **No regressions:** Existing tests must continue passing.
8. **No fake validation:** Report only tests and checks actually performed.
9. **Protect existing work:** Do not overwrite pre-existing uncommitted changes.
10. **Documentation:** Document important technical decisions and limitations.

## Phase Completion Protocol

At the end of EVERY phase, produce a concise report containing:

- Phase completed.
- Implementation summary.
- Files created or modified.
- Tests executed and actual results.
- Existing tests passing/failing.
- Regressions discovered and resolved.
- Remaining risks and limitations.
- Whether the next phase's prerequisites are satisfied.

Then:

- If validation succeeds, automatically proceed to the next phase.
- If validation fails, fix the issue and rerun the relevant tests.
- If a blocker cannot be resolved safely, stop and report it.
- Never skip a failed validation to maintain progress.

## Final Deliverable

After Phase 7, provide a consolidated report covering:

- Final architecture and printing workflow.
- All files added, modified, and removed.
- Dependencies and their purpose.
- Test and build results.
- LAN and Windows printing validation.
- Physical printer testing status.
- Remaining limitations and production risks.

The migration is complete only when the implementation, regression validation, and final review are finished.
